مجوز مشخص HTTPS/Trust با Fingerprint واقعی و ایجاد Release Owner/Reader
دریافت و اجرا شد. [شواهد آماده‌سازی](../evidence/v0.1.5/https-owner-preparation-20261014.md)

## A — HTTPS

بررسی فقط‌خواندنی: روی `gitlab-master`، Nginx خود Omnibus فعال است،
`external_url 'http://gitlab.local'` و SSH port برابر ۲۲۲۲ است؛ پورت ۴۴۳ و
دایرکتوری `/etc/gitlab/ssl` وجود ندارند. Ubuntu نام را به `192.168.122.230`
resolve می‌کند. Private Key یا Secret خوانده یا نمایش داده نشده است.

راهکار پیشنهادی، استفاده از Nginx موجود با گواهی صادرشده توسط CA داخلیِ
مورد تأیید مالک محصول و SAN برابر `gitlab.local` است. صادرکننده و Fingerprint
CA باید پیش از اعتماد مشخص شوند. گواهی و زنجیره باید معتبر، غیرمنقضی و دارای
کاربری Server Authentication باشند؛ Agent گواهی جعلی یا Root جدید نمی‌سازد.
نمونهٔ تنظیم در
[`gitlab-https.rb.example`](../../deployment/release/gitlab-https.rb.example)
قرار دارد و خودکار اجرا نمی‌شود.

پس از مجوز مشخص:

1. مالک محصول/مدیر زیرساخت Certificate/full chain و Key را از صادرکنندهٔ
   تأییدشده روی `gitlab-master` فراهم کند. Key فقط root-readable باشد و از
   Chat/Repository/Job Artifact عبور نکند. تنظیم فعلی و فایل‌ها Backup شوند.
2. با مجوز تغییر `external_url` و Nginx، Template با تنظیم موجود reconcile
   و `gitlab-ctl reconfigure` اجرا شود. HTTP به HTTPS هدایت شود؛ SSH Remote
   موجود روی ۲۲۲۲ حفظ می‌شود. اثر جانبی: وقفهٔ کوتاه وب/API و نیاز به اصلاح
   URL/Trust در Runnerها؛ پنجرهٔ maintenance لازم است.
3. مجوز Trust تنها برای CA با Fingerprint تأییدشده و میزبان‌های مشخص ثبت شود.
   در Runnerها ابتدا `tls-ca-file` اختصاصی و Trust محدود Client ترجیح دارد؛
   Powershell/.NET روی Windows برای زنجیرهٔ خصوصی به Trust معتبر Windows
   نیاز دارد، پس تغییر Store جداگانه باید صریحاً مجاز باشد.
4. روی `mani-pc`، `win10-runner` و مسیر Release، ابزارهای فقط‌خواندنی
   [`check_gitlab_https.py`](../../tools/release_sync/check_gitlab_https.py) و
   [`Test-GitLabHttps.ps1`](../../deployment/release/Test-GitLabHttps.ps1)
   اجرا شوند. پاسخ ۴۰۱ به درخواست بی‌Token طبیعی است؛ PASS فقط صحت TLS و
   دسترس‌پذیری API را اثبات می‌کند، نه مجوز انتشار.
5. تنظیم Runner URL به HTTPS و checkout Git/API بررسی شود؛ به Secrets دست
   نزنید. هیچ `--insecure`، `verify=false` یا certificate callback مجاز نیست.

Rollback زیرساخت فقط با تنظیم Backup و برنامهٔ مجاز انجام شود؛ هیچ Restore
Snapshot یا تغییر دیسک VM بخشی از این دستورالعمل نیست.

منابع رسمی: [Omnibus HTTPS](https://docs.gitlab.com/omnibus/settings/nginx/)،
[Runner TLS](https://docs.gitlab.com/runner/configuration/tls-self-signed/).

## B — Release Owner واقعی و مستقل

Tag actor فعلی حساب `root` با ID برابر ۱ است. Owner باید یک انسان واقعی با
User ID متفاوت باشد؛ Bot یا Approval صوری قابل قبول نیست. حداقل نقش
Developer برای بررسی/Approve MR کفایت می‌کند؛ Owner به Admin، ساخت Tag یا
مجوز انتشار نیاز ندارد. ساخت/دعوت حساب یا اعطای نقش، اقدام مالک محصول است.

ناشر جدید علاوه بر record، عضویت فعال Owner و Approval واقعی را از API
می‌خواند و Commit نهایی را با `merge_commit_sha` همان MR روی Main تطبیق
می‌دهد. `CI_JOB_TOKEN` مجوز خواندن Approvals API ندارد؛ credential خواندن
`read_api` باید با مجوز مالک محصول فراهم شود. آن credential در کد فقط GET
اجازه دارد، Redirect نمی‌پذیرد و برای نوشتن Release به کار نمی‌رود.

متغیرهای زیر فقط توسط مدیر مجاز در Settings → CI/CD → Variables، با دامنهٔ
انتشار محافظت‌شده تنظیم شوند؛ Agent آنها را نمی‌سازد یا مقدارشان را نمایش
نمی‌دهد:

| Variable | نوع/حفاظت | هدف |
|---|---|---|
| `MT5_RELEASE_OWNER_USER_ID` | Protected، مقدار عددیِ غیرمحرمانه | هویت Owner واقعی |
| `MT5_RELEASE_APPROVAL_TOKEN` | Protected / Masked / Hidden؛ `read_api` | خواندن Approval؛ بدون مجوز نوشتن یا افشا |
| `MT5_RELEASE_AUTHORIZATION_FILE` | Protected، File type، JSON غیرمحرمانه | record دقیق Tag/Commit/Owner/MR و تصمیم ریسک‌ها |
| `MT5_RELEASE_INSTALLER_ACCEPTANCE_FILE` | Protected، File type، JSON غیرمحرمانه | رسید واقعی Windows برای Hash همان Artifact |

انتقال record از فایل tracked به Protected file variable، مشکل ارجاع
ناممکنِ یک Commit به Hash خودش درون همان Commit را رفع می‌کند؛ شرط اتصال
دقیق Tag/Commit و استقلال Owner حذف نشده و بررسی واقعی API افزوده شده است.
این تغییر محل نگهداری record و تنظیم متغیرها باید در مجوز تنظیمات حساس
GitLab صریحاً پذیرفته شود. record باید پس از مشخص‌شدن Commit نهایی، از
Approval واقعی ساخته شود و بعداً نسخهٔ پاک‌سازی‌شدهٔ آن در Release Asset
آرشیو می‌شود. رکورد نمونهٔ جعلی برای نسخهٔ واقعی به Repository اضافه نشود.

منابع رسمی: [Approval API](https://docs.gitlab.com/api/merge_request_approvals/)،
[حدود Job Token](https://docs.gitlab.com/ci/jobs/ci_job_token/)،
[نقش Approver](https://docs.gitlab.com/user/project/merge_requests/approvals/rules/)،
[File variables](https://docs.gitlab.com/ci/variables/).

## ترتیب انتشار پس از رفع A/B

ابتدا همهٔ گیت‌های Branch و Artifact جدید و آزمون Windows آن PASS شوند.
سپس Feature→Develop→Staging→Main با Pipeline هر مرحله و بررسی واقعی Owner
انجام شود. Tag annotated فقط به Commit تأییدشدهٔ Main اشاره کند.

Tag Pipeline یک Installer با رسیدهای همان Pipeline می‌سازد. Job ناشر
`when: manual / allow_failure: false` است و تا تأیید عملی دقیق همان Hash و
recordهای محافظت‌شده منتشر نمی‌کند. اگر باینری Tag با کاندیدای آزموده‌شده
متفاوت باشد، آن Artifact باید واقعاً نصب و بررسی شود؛ رسید #98 یا Branch
نباید به Tag Pipeline نسبت داده شود.

Acceptance JSON به طور دقیق باید این فیلدها را داشته باشد:

`schema_version=1`, `status=PASS`, `source_commit`, `pipeline_id`,
`installer`, `sha256`, `installer_size_bytes`, `installer_build_job_id`,
`installer_verify_job_id`, `installer_exit_code=0`, `service_session_id=0`,
`agent_session_id=0`, `worker_session_id>0`, `mt5_session_id`,
`health_worker_session_id`, `freshness=FRESH`, `mt5_connected=true`,
`no_trading=true`, `soak_seconds>=900`, `soak_samples>=30`,
`soak_failed_samples=0`, `captured_at`.

Publisher پس از بررسی TLS، Owner/API، رسیدها و Hashها، فایل‌ها را در Generic
Package Registry داخلی ذخیره و دانلود/Hash می‌کند؛ سپس Release را می‌سازد
و مجدداً می‌خواند. Assetها شامل Installer، Manifest، Sidecar، SHA256SUMS،
Provenance، پذیرش Windows، Authorization و Release Notes هستند. Job artifact
دارای انقضا، لینک رسمی دائمی محسوب نمی‌شود.

کانال پیش‌فرض `internal` است. Job و CLI انتشار GitHub در این کانال قبل از
خواندن credential یا درخواست شبکه رد می‌شوند. Mirror منبع مخزن تغییری
نکرده است؛ فعال‌سازی `public` و انتشار بیرونی نیازمند مجوز جداگانه است.


## مسیر محتوای Approval بعد از آماده‌سازی

Owner واقعی ID 3 / release-owner با نقش Developer، خودش در UI GitLab Approve
می‌کند و JSON Authorization دقیق را در یک Note جدیدِ MR مرتبط ثبت می‌کند.
Note نباید edit شود؛ برای تصحیح، Note جدید ایجاد شود. Protected File باید
عین همان JSON باشد و فقط `approval_note_id` واقعی به Metadata آن افزوده شود.
Publisher Author، native approval، Main merge SHA، timestamps و محتوای Note
را بررسی می‌کند؛ Maintainer/CI حق صدور تصمیم به نام Owner ندارند.

در مرحلهٔ فعلی، Approval اولیهٔ Owner برای Promotion لازم است. Approval و
Note نهاییِ Release باید با MR Main و Artifact واقعی همان Tag نیز منطبق شوند.
هیچ evidence مربوط به #102 نباید به Artifact متفاوت Tag نسبت داده شود.


## ثبت صحیح تصمیم انسانی و Audit Trail

Owner باید از کادر Comment جدید و حالت متن خام/Markdown استفاده کند؛ Escape کردن براکت‌های JSON توسط Rich Text باعث رد Parser می‌شود. زمان ISO-8601 باید timezone داشته باشد؛ `2026-10-14T07:13Z` با قرارداد فعلی معتبر است. زمان واقعی را خود Owner تعیین می‌کند. هیچ maintainer/agent حق اصلاح یا صدور تصمیم به نام Owner ندارد.

Publisher `author.id=3`، human/non-system Note، `created_at=updated_at`، JSON دقیق، MR merged به main و SHA همان Tag را کنترل می‌کند. Note #23 JSON نامعتبر داشت؛ #25 ابتدا نامعتبر و بعد ویرایش شد و رد شد؛ #26 مستقل، صحیح و ویرایش‌نشده است. Notes قبلی حذف یا ویرایش نمی‌شوند. انتقال همان JSON به Protected File فقط افزودن server-assigned `approval_note_id` به Metadata است؛ هیچ محتوای تصمیم تغییر نمی‌کند.
